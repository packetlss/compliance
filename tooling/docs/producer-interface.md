# Experimental producer interface

The interoperability contract is an ordinary typed Evidence JSON document. The
`compliance producer` commands expose existing schema contracts for developers;
command names and JSON responses are experimental, without a compatibility freeze.
They need no project configuration, Control IDs, desired policy, OPA, or Git.
They do not read a nearby `compliance.yaml` when invoked as shown below.

## Explicit discovery and export

Install `compliance-tooling` and separately materialize the policy artifact you
intend to use. Installing tooling does **not** install policy-owned Evidence
schemas. `POLICY` below is the explicitly supplied semantic root of that artifact,
not a repository or a schema URL. The developer need not locate its schema files.

```sh
compliance producer list --policy-source library="$POLICY"
compliance producer schema --policy-source library="$POLICY" \
  --type linux.packages/v1 > package-schema.json
```

`list` returns `kind` and `contracts`, whose entries contain exact `type` and
`schema_id` values. `schema` writes only the canonical schema definition as JSON
on stdout. It preserves all authored schema content and local references; JSON
whitespace/key order may differ from the source file. `--schema-id URI` optionally
asserts that the selected type has that exact schema URI. Unknown types, mismatched
URIs, invalid schemas and unresolved references fail with exit 2 and a diagnostic
on stderr. There is no network lookup, fallback or schema rewriting. Reference preflight
uses the specification-defined subschema locations from `referencing`; opaque
annotation values remain authored content even when they contain `$ref` or
`$dynamicRef` keys. Genuine schema references are still resolved offline.

Repeat `--policy-source NAME=PATH` for independent sources. Every supplied root
must exist. Catalog admission remains fail-closed: exact-identical definitions
across sources coalesce; divergent definitions fail irrespective of source order.
Paths are acquisition/diagnostic locations, never schema lookup identity. The
catalog retains the complete authored schema separately from internal locators so
export and exact-definition comparison include underscore-prefixed annotations.

An exported schema is a developer convenience. It is not a composed policy artifact,
release descriptor or substitute composition, and makes no claim to the originating
artifact's full content digest. Standalone validation continues to use explicitly
supplied policy roots; this tranche adds no exported-schema registry/import format.
The schemas and their distribution ownership remain with the policy artifact.

## One-document validation

```sh
compliance producer validate --policy-source library="$POLICY" \
  --type linux.packages/v1 --input evidence.json
cat evidence.json | compliance producer validate --policy-source library="$POLICY" \
  --type linux.packages/v1 --input -
```

Success exits 0 and emits `document_valid: true`, `validation_scope: document-only`,
`kind`, `type` and `schema_id`. Failure exits 2, emits a diagnostic on stderr and
no success JSON. Validation never writes or repairs the input.

The input must be one UTF-8 JSON object with unique member names. The complete
object, including extensions, must be representable by the existing RFC 8785/JCS
implementation: non-finite numbers, out-of-range integer values and invalid Unicode
are rejected. Schema validation uses the existing offline Draft 2020-12 Evidence
validator and its explicit timestamp format checker. A generic JSON Schema
validator with different format/representation handling is not equivalent.

The caller supplies `id`. No identity is generated by the CLI or the example
collector, and no new identity algorithm is introduced. All schema-permitted
extensions survive ordinary construction/serialization and remain complete-document
identity-bearing content; that does not declare them as criterion inputs.

Document validity establishes neither observation truth nor assessment admission,
freshness, selection, applicability or a PASS/FAIL/UNKNOWN outcome. For example,
the reviewed observation from 2000 is document-valid. Assessment still applies its
own exact subject/type routing, candidate validation, freshness, ambiguity and
provenance rules; policy still owns complete criteria.

## Small Subject check

```sh
compliance producer list --kind subject
compliance producer schema --kind subject > inventory-schema.json
compliance producer validate --kind subject --input subject.json
```

This uses the existing tooling-owned, installed inventory resource schema and
requires one normalized `kind: Subject` resource (the `apiVersion`, `metadata`,
`spec` authoring representation, not an internal operator view). The exported
schema is the complete canonical inventory schema, retaining its local `$defs`;
`$defs.subject` is the Subject branch. Evidence source/type options are rejected
for this check. The same supported JSON representation and timestamp checker apply.

The [authored Subject example](../examples/producer/subject.json) supplies governed
facts separately from observations. `spec.attributes` remains adapter-specific
content, not applicability labels. This check does not validate a whole inventory,
identity uniqueness, group DAG, assignments or references, nor authenticate upstream
facts or establish completeness. Use `inventory validate` for catalog validation.

## Reproducible installed/no-Git collector exercise (#186)

From a clean committed candidate with the repository toolchain prepared:

```sh
scripts/dev gate package
```

The gate builds and installs the wheel in a new venv, then copies the control-library
policy root, its [reviewed producer examples](../../policy-sources/control-library/examples/producer/README.md),
the Subject example and the scenario-owned
[exercise](../../verification/scenarios/scripts/assert-producer.py) to a fresh
outside-repository runtime directory. Git and OPA commands are blocked there.
There is no project config, `.git`, `PYTHONPATH` or checkout location in collector
arguments. All temporary exports/observations are removed by the gate.

The exercise performs these public steps (with local materialized paths):

```sh
compliance producer list --policy-source exercise=policy
compliance producer schema --policy-source exercise=policy \
  --type linux.packages/v1 > package-schema.json
python -I -S examples/collect_packages.py \
  --id evidence:external-example:001 --subject host/producer-example \
  --collected-at 2000-01-01T00:00:00Z \
  --observation examples/package-observation.json > evidence.json
compliance producer validate --policy-source exercise=policy \
  --type linux.packages/v1 --input evidence.json
compliance producer validate --kind subject --input subject.json
```

Expected success is `document_valid: true` with `validation_scope: document-only`.
It also checks file/stdin equivalence, all 11 policy-owned conformance vectors,
complete extension preservation against the authored example, Subject discovery and
export, invalid Subject time, and missing policy schemas with tooling alone. The
collector runs with `-I -S`, so it cannot import the installed `tools` package; it
uses only Python's standard library. It observes synthetic input, not a real Linux
host or package manager. No SDK or builder is involved.

The canonical scenario gate separately runs
[`assert-producer-criteria.py`](../../verification/scenarios/scripts/assert-producer-criteria.py).
It gives the unchanged observation to the existing required-package and
only-allowed-package Rego criteria. Each produces pass and fail for different
policy parameters. This is evaluator-side criterion reuse, explicitly bypassing
assessment admission; it is not a claim that the old observation qualifies for a
current assessment. The collector receives none of those policy inputs.

The exercise is a bounded falsification, not a freeze or production-readiness test.
The PR records the run and actual friction. Ordinary construction is sufficient
when the example, schema and document diagnostics make the contract usable; any
concrete need for generated bindings requires subsequent reassessment/promotion.
